## D3. Can a script port the app to the web?

**The idea.** Use something like Tokamak so that one script reads the app's source, rebuilds it for the browser, and gets run whenever the web demo needs updating. No cross-platform rewrite up front, and no doing every new feature twice.

**Short answer.** The idea is sound in principle, and it is the right shape. The tool is the problem, and so is the app. As things stand it would be a refactor of most of the app, not a script. I recommend keeping D3 parked, and when a demo is wanted, doing option C first.

### What Tokamak is

Tokamak is not a converter that reads SwiftUI and writes HTML. It is a library that copies SwiftUI's API for the browser. You change `import SwiftUI` to `import TokamakShim`, the same Swift is compiled to WebAssembly with the SwiftWasm toolchain, and the views draw themselves as HTML elements. So there is no translation step to get wrong, which is what you were after.

### Why I would not build on it

- **It has been shut down.** Its GitHub repository was archived on 28 Jan 2026 and is read-only. The last release was 0.11.1 in November 2022. (From the project's GitHub and package pages.)
- **It covers a small part of SwiftUI.** Its own README says it implements a very basic subset. Anything missing would have to be added by us, in a framework nobody maintains.
- **Newer projects exist but are young.** A search found SwiftWasmUI (tiny, almost no users) and ElementaryUI (SwiftUI-inspired but not SwiftUI-compatible, so the views would have to be rewritten against it). I have not tried either.
- **It would not look identical.** The browser version works out layout with CSS, so spacing, fonts, sheets and animations would differ from the phone. Close, not the same.

### What in Anchor blocks it

I searched the source (71 Swift files, about 35,000 lines). These are file counts.

| Dependency | Files | What it means for a web build |
| --- | --- | --- |
| `import SwiftUI` | 62 | The part a Tokamak-style tool is meant to cover, but only partly. |
| `import SwiftData` | 50 | There is no SwiftData in the browser. `@Query` is used in 38 files. The whole data layer needs a stand-in. This is the big one. |
| About 20 other Apple frameworks, one to five files each | HealthKit, WidgetKit, ActivityKit, EventKit, MessageUI, PhotosUI, PencilKit, MusicKit, LocalAuthentication, JournalingSuggestions, Charts, AVFoundation, ContactsUI, UserNotifications, CryptoKit and more | Each needs a pretend version for the demo, or has to be left out. |
| `NavigationStack` | 27 | Used everywhere. |
| `.sheet` | 36 | Used everywhere. |
| `.toolbar` | 40 | Used everywhere. |
| `Menu` / `DatePicker` / `TextEditor` / `Canvas` | 17 / 12 / 8 / 2 | Common places for gaps. |

I did not check each of those against what Tokamak supports. They are the ones I would expect to be gaps.

### What it would take

1. Move the screens into a Swift package that does not import Apple-only frameworks directly, with everything platform-specific behind small protocols.
2. Write a browser stand-in for SwiftData, fed from the showcase seed that already exists.
3. Write pretend versions of the other frameworks (a fake Health, a fake Reminders, and so on).
4. Write the build script that compiles the package to WebAssembly and publishes it.

After 1 to 3, an update really would be one script run, as you want. But 1 to 3 touch most of 35,000 lines of code, none of which is confirmed building yet. That is a lot to add to a branch that has not had a clean build.

### Options now (point 25 in the plan)

| Option | Update by running a script? | Real, working app? | Cost |
| --- | --- | --- | --- |
| A. React rebuild fed from the shared seed | No, UI changes are ported by hand | Looks like it | Small, but double work for features |
| C. Screenshot click-through generated by the UI tests that already exist | Yes | No, tapping hot spots on screenshots | Small |
| D. Cross-platform rewrite (React Native or similar) | Yes | Yes | The whole app |
| **E. Compile the real Swift for the browser (this question)** | Yes, once set up | Yes, close but not identical | A refactor of most of the app, on a framework that is archived |

### My recommendation

Keep D3 parked, as D4 and D9 already say. When you want a demo, build option C: it is the only one that meets "run one script when I want to update it" without a refactor, and it costs little. It is not a working web app, and I would say so on the page.

If you would still like to learn whether E can work, there is a cheap test: one self-contained screen (Affirmations, say) built for the browser in a separate package, to see whether the toolchain and the framework hold up, before anything is moved. That does not touch the app.

**To answer, reply:** `D3: parked`, `D3: option C`, or `D3: try the one-screen test`.

### Your answer, and what it changes (9 Nov 2026)

**Decided:** park D3 until the end, just before the Android work and the other awkward extras.

**What you want from the demo:** a script you run when you want the demo updated. It shows the screens and features with demo data. It does not have to work as a real app. It has to look close enough to be the same at a glance, and build itself from the app's demo data and how the app really looks. Data can behave like a session store that clears on refresh. Health, Journaling Suggestions, Photos and the other Apple-only parts can be small pretend placeholders that show what the feature does without doing it.

**Why that is a lighter job than the one I assessed above.** Two of the hardest items in the table, the SwiftData stand-in and the Apple frameworks, mostly disappear, because nothing has to really work. What is left is one thing: something has to draw the screens in a browser. There are two ways to do that, and the choice can wait until the work starts.

1. **Swift in the browser.** Compile the real screens for the web with a SwiftUI-style framework. It stays a live, tappable app, but it needs a framework that is still maintained (Tokamak is not), and a lot of screens may need small changes.
2. **Generated from the running app.** A script starts the app in showcase mode on the simulator, visits each screen, and records the picture of it plus where every button, label and field sits. A second script turns that into web pages where tapping a button goes to the next screen. Because it starts from the real app's own picture, it looks the same by construction, and it updates by running the script again. Typing and anything that needs real behaviour would be faked. I lean towards this one, since your goal is looking identical, not working identically. I have not built either.

**What helps in the meantime, and is already done:** the showcase mode and its made-up content for every kind of content (RV7), and the guide registry. Both are what the demo script would read. Nothing else needs to change now.

**Where it sits:** Patch 55 in Phase H, last, before the Android work.

## D15. How should locked text be kept in the database? (in plain words)

### Answer (9 Nov 2026): option B, with a safety copy and a way back first

**What you decided:** lock every model in one go (option B). Before anything is locked or moved, make a backup of all the data, and make going back easy, so that nothing can be lost.

**How I am building it.** B stays one switch for you, but it is written as three pastes so that the way back exists before the lock does:

1. **35b1, the safety copy and the way back.** Anchor makes an exact copy of everything it has saved: the database, the voice notes and the Journal photos and drawings. It is made when Anchor starts and before the database is opened, because a copy of a file nobody is writing to cannot be half old and half new. Every file is checked against its fingerprint. Go back puts the copy in place, and Undo go back reverses that. This works on its own, with no locking, and you can try it first.
2. **35b2, the new stored fields.** Each text field gets a second stored field beside it. Nothing is locked yet, and everything reads as before.
3. **35b3, Lock my data.** One flow: checks your recovery key, asks you to keep an encrypted backup off the phone (the existing Make an encrypted backup), takes the safety copy, locks every model, then checks that every item is still there and that every locked value opens to exactly what it was. If anything is off, it goes back by itself and tells you.

**What I read "back up all the data that isn't touched by the encryption" as.** I made the copy cover everything, including the voice notes and photos (which locking the text does not touch) and the database itself (which it does). If you meant only the files, say so, but I think the whole copy is what makes a rollback possible.

**What this can and cannot promise.** I cannot promise zero risk, and I would not trust anyone who did. This is what it does promise:

- Nothing in the database is changed until the copy exists and has been checked.
- Going back returns you to exactly that copy. Anything you wrote after it was made is set aside, not deleted, and Undo go back brings it back.
- A failed lock goes back by itself.

And this is what it cannot do:

- **It sits on the same phone.** If the phone is lost, broken or wiped, the copy goes with it. That is why 35b3 asks for an encrypted backup kept somewhere else first, and will not start until you say you have one.
- **It is a plain copy.** While it exists, a copy of the phone's files shows your data readable, which is exactly what locking is meant to stop. It is kept out of phone backups and given the phone's file protection, and you delete it once you are happy. Clear all data deletes it too.
- **Going back loses nothing, but it does not merge.** Entries made after the copy are in the set-aside folder and can be brought back with Undo go back, but they do not appear alongside the older data. The way to keep them is to go back as soon as something looks wrong, before writing more.
- **It needs a restart.** Making the copy and going back both happen when Anchor starts. The screen says so, and tells you to close Anchor from the app switcher and open it again.
- **Settings, keys and widget summaries are not in the copy.** The lock does not change them.

I have not run any of this. It is written without a compiler and needs a build and a try on your phone, on a copy of your data, as every patch does.


### The picture

Your journal is stored in one file on the phone. Think of that file as a paper diary.

- **Right now,** the diary sits in a drawer. The drawer is locked when the phone is switched off or just restarted. Once you have unlocked the phone, the drawer is open to the app. If someone gets a copy of the diary file (for example from a backup of your phone saved on a computer, with no backup password), they can read it like any other document. That is how I understand it works; I cannot test it here.
- **Locking the text** means the words in the diary are written in a secret code. A copy of the file is just gibberish. The app has the key to the code, kept safe on your phone only, and turns the gibberish back into words when you open an entry. You notice nothing as you use the app.

Already built: the key, and the 28 character recovery key you would be shown once. Not built: actually writing the secret code into the diary. That is Patch 35b, and the question is how careful to be when doing it.

### Why this is scary

To switch the diary to secret code, the app has to change how the file is laid out, and rewrite the entries already in it. If that goes wrong halfway, entries could be lost or the app could refuse to open the file. I cannot run it here, and nobody has run it on your real data. That is the whole reason there is a choice.

### Option A: scramble the journal first, check it, then do the rest

**What it does:** Patch 35b scrambles only the journal entry text. You try it on your phone. Then a later patch (35c) does messages, safety plan, Boundaries, goals and notes.

**Why you might want it:** the journal is the most private thing in the app. If something goes wrong, only the journal is at risk, and you find out before everything else is changed. It is the careful route.

**What it costs:** it takes two patches, and you have to test in between. Until 35c, your messages and safety plan are still readable in a file copy.

### Option B: scramble everything at once

**What it does:** one patch, one big change, every piece of text scrambled together.

**Why you might want it:** it is the quickest way to finish, and everything is covered from the first day. You test once.

**What it costs:** if it goes wrong, everything goes wrong together, and it is harder to tell which part broke. It is the riskiest way.

### Option C: do not scramble the file at all

**What it does:** nothing changes in the file. The phone's own protection stays (locked when off, the app lock on top), and exports and backups can still be password protected.

**Why you might want it:** zero chance of damaging your data. It is the least work. If only you use the app on a phone with a passcode, it may be enough.

**What it costs:** a copy of the file stays readable. And the recovery key and the key work already built would have no job, which goes against what you chose earlier in D5.

### Things that change in the app if you pick A or B

- You are shown a recovery key once, and must keep it. Lose both your phone's key and the recovery key and the locked text is gone for good. Nobody, including me, can get it back.
- A new phone or reinstall asks for the recovery key before the text opens.
- Searching the journal might be slower, since the app has to unscramble entries to search them.
- Widgets cannot show locked text. They already use their own separate summary, so they keep working.
- Old entries that were readable before may still leave readable traces in unused parts of the file. I cannot confirm whether they do. New writing is covered best.

### My pick, and who it is for

- Pick **A** if you want the promise in D5 kept and want to be careful. It is my recommendation.
- Pick **B** if you would rather get it over with and are willing to test hard, with a full backup made first.
- Pick **C** if you decide the risk of touching the file is worse than the risk of someone copying it.

### Two details that are mine to settle, not yours

- Whether to change the old field's name or add a new one beside it. Adding is the more routine kind of change, so I lean that way for the first model.
- Whether locking is automatic or a switch you turn on in Settings. I lean towards a switch, so you see the recovery key at the moment you turn it on.

**Answered:** B, see the top of this section.

A trigger window is a time you marked as hard, such as Sunday evening. Anchor can remind you when it starts. ### D21 (e). The plain screen over the app switcher

When you swipe up on an iPhone to see your recent apps, each app is shown as a small picture of the last screen it had open. In showcase mode Anchor lays a plain screen over the picture, so the switcher shows a blank card, not whichever made-up page happened to be open. Honestly, the gain is small, because the made-up pages are not private. It is there as a safety margin: it also covers the moment of switching in or out, and it means a person flicking through your apps cannot see the demo and ask what it is. It does not cover a sheet that is open. It costs nothing to keep and one overlay to remove. It stays as built until you say otherwise.

### D22 (d). Why the widgets' key is a file and not a Keychain item

The widgets on your home screen are a separate small program from the app, and they need to open the locked summary, so both programs need the same key. There are two ways. A Keychain item shared between the two is the tighter one, but it needs a new capability switched on in Xcode for both programs and edits to two settings files, and I cannot test any of that from here, so a mistake would show up as widgets that go blank. A key file in the folder the two programs already share, marked as left out of backups, needs none of that and I could test the format. The cost: someone with file access to a running, unlocked phone could read the key file, as they could read the summary before. It stands unless you say, and the Keychain version replaces only two functions.
