# Optional extras: iCloud sync, voice, and AI tools

Written 9 Nov 2026 (change log 123). Built so far: the one switch (AI0) the consent sheet with the Apple on-device provider (AI1, change log 141), the AI Optimised block in the Journal (AI2, change log 143, D52), Break into steps and Estimate time on a task (AI3, change log 144, D53), Tidy a braindump (AI4, change log 146, D54), Ollama on your own computer (AI5, change log 148, D55), dictation in the Journal (VN1, change log 150, D57), the greyed-out buttons while AI tools are off (AI7, change log 164, D65), Ollama away from the home network (AI8, change log 165, D66), and AI Optimised versions in exports as two labelled entries (AI9, change log 166, D67); the rest is not built. Every claim about the code was checked in the repo; claims about Apple's frameworks are from memory and are marked **check** where a spike must confirm them before a patch promises anything. The patches are in Phase I of `ANCHOR_PATCH_PLAN.md`, the questions are D38 to D43 in section 0.4.

## The rules that apply to all of it

1. **Everything here is optional and off by default.** A person who never opens Settings never sees any of it.
2. **Nothing is assumed, inferred, generalised or collected.** A feature works only on what the person selected, only when they press its button, and its result is a suggestion until they keep it.
3. **The original is always kept and always one tap away.** Nothing rewrites, replaces or deletes what the person wrote.
4. **AI is a formatting and accessibility tool, not a feature to sell.** Never front and centre, never a chatbot, never a "how are you feeling" conversation, never on by default, never pushed in onboarding, the tour, the website or the App Store text. It is a button like any other button.
5. **Local first, and cloud is only ever an option the person adds themselves.** The app never suggests, names, preselects or recommends a cloud model.
6. **Send the least possible.** The model receives only the text the person selected for that one action, plus a fixed instruction. No names from Contacts, no other entries, no dates, no history, no device details.
7. **Keep nothing longer than needed, and say how long.** The answer is held in memory until the person keeps or discards it. No logs, no analytics, no "improve the product" use. Whatever is kept is the person's own entry, in their own store, locked and backed up like everything else.
8. **Ask every time, unless told not to.** Each use shows what will be sent, to which provider, and what that provider does with it. "Don't ask again" is a switch the person turns on, per feature and per provider, and can turn off again.
9. **One switch turns all of it off.** See E5.
10. **UI wording follows the plan's rules:** plain verbs ("Make shorter", "Break into steps", "Turn into tasks"), no "AI-powered", no "smart", no sparkle icons, no emoji, no em dashes.

## E1. Optional iCloud storage, for sync between your own devices

**What it is.** A switch in Settings, off by default, that keeps the same Anchor data on every device signed in to the same Apple ID. Anchor has no server and never will; the only place data goes is the person's own private iCloud space.

**What "secure" means here.** Two layers, and the second is what matters. CloudKit's private database is only readable by the person's Apple ID and is encrypted in transit and at rest, but Apple holds the keys unless the person has turned on Advanced Data Protection. So the second layer is Anchor's own field-level locking (point 20, D15 option B, patches 35b1 to 35d): by the time anything reaches iCloud every text field is already ciphertext, so Apple, and anyone who ever got into the iCloud account, sees nothing readable. **That is why sync comes after the locking work and never before it.**

**What the code says today** (checked): `AnchorSchema.makeContainer` has a comment saying there is deliberately no CloudKit. All 34 models declare `@Attribute(.unique) var id: UUID`, and SwiftData stores that sync through CloudKit cannot carry unique constraints. So the first sync patch is not about sync at all: it removes the constraint from every model and has the app itself keep ids from doubling up. That is a store migration, so it needs the safety copy (35b1) first. **Done in SY0:** no model declares `.unique`, the backup import records each id as it adds it, and `scripts/check-no-unique-ids.mjs` keeps it that way.

**Rules for sync.**
- **Off by default, turned on in Settings, with a plain screen saying what leaves the phone and where it goes.** Turning it off stops syncing and leaves each device's copy as it is; nothing is deleted anywhere without being asked.
- **Per-device things stay per-device:** reminders (each device schedules its own), the widget summaries, the app lock, the showcase mode switch and its passcode, the review run, and which widgets show where.
- **Showcase mode never syncs.** The demo store is in memory and the real store is not opened while it is on.
- **Sleep stays out of the first version** (D39). `docs/SLEEP.md` already notes Apple's rule that health information must not be stored in iCloud, and Apple Health nights are exactly that.
- **Voice notes and Journal photos** are files, not rows. They travel as CloudKit assets in a second step (SY2), and only after 35d has locked them.
- **Deleting means deleting everywhere.** "Clear everything" says plainly that it also removes the data from the other devices. A way back is the safety copy on each device, not iCloud.
- **Conflicts:** the same record edited on two phones at once keeps the later edit, which is what CloudKit does. Text is never merged line by line. **Check** whether a conflicted text field is worth keeping both versions of; the first version does not.
- **The key** (D40): a second device needs the data key before it can read anything. Either the recovery key is typed on the new device (nothing travels), or the key is put in iCloud Keychain, which Apple also encrypts end to end, if the person turns that on. Recommendation in D40.
- **Needs from you in Xcode:** the iCloud capability with CloudKit on the app target, a container, and a first run on two real devices. Neither can be tested in a simulator pair.

## E2. Dictation and voice notes together, for journalling

**What it is.** In the Journal editor, a Dictate button. While it runs, what is said appears as text in the entry as it is spoken, **and** the audio is recorded as a voice note at the same time. When it stops, the person chooses what to keep: the text, the audio, or both. Keeping only the text deletes the audio file.

**How it is built.** One microphone tap feeds two things: a file writer (the voice note path from 14b) and the speech recognizer. **On-device recognition only.** If the language is not available on the device, the button says so and does not fall back to Apple's servers. Recognition is a text-in-progress that the person can edit, like any typed text; nothing about it is stored beyond the entry's text.

**Permissions.** The microphone string today says voice notes "you choose to attach to a message" and must be widened; speech recognition needs its own usage string. Both are written in the plain words the plan uses. The privacy page is updated in the same patch.

**Telling people apart (D38).** When more than one person is talking (a session, a conversation the person wants to remember), the transcript can be split into turns labelled **Speaker 1, Speaker 2**. The person can rename a label to plain text for that entry only ("Mum", "Dr Lee"). **Nothing about a person is stored:** no voiceprint, no profile, no list of names, nothing that would recognise the same voice in a later recording. A voiceprint is biometric data about someone who never agreed to it, and the rule is not to hold people data. Labels live inside the entry's own text like every other word in it.
**Check first (spike VN3):** whether Apple's current speech APIs separate speakers at all. As far as I know the transcript comes back without speaker turns, so the first version may be a manual label, "Who is speaking?", tapped as the speaker changes, which needs no recognition of voices and stores nothing. A model that separates voices would be an on-device option only, and only if it passes the same rules.

**As built in VN1.** Settings, Journal, Dictate in the Journal is a switch of its own, off to begin with, and not part of the AI switch because nothing about it is AI tools in the sense of E5: the words are turned into text on the phone and go nowhere. When it is on, a microphone button joins the row of tools on a Journal page. The words heard so far appear after what is already in the paragraph being written in (or the last paragraph), and tapping the microphone again stops it. Typing in that paragraph while it listens stops it and leaves the typing alone. It also stops when Anchor leaves the screen, on a call, and after 5 minutes. Recognition is on the device only (`requiresOnDeviceRecognition`), and if the phone cannot do the language of its own settings, Dictate says so and does not start, before any permission is asked. The sound is passed to the recogniser in memory and is never written to a file; keeping a voice note as well is VN2. The code is `Support/Dictation.swift`, the only file that may use speech recognition, which `scripts/check-dictation.mjs` enforces. It uses the older `SFSpeechRecognizer`; **check** whether Apple's newer speech analysis APIs do better on long recordings before VN3.

**As built in VN2.** Settings, Journal has a second switch, Keep a voice note while dictating, off to begin with, shown only while Dictate is on and never in showcase mode. With it on, the one microphone feed goes to the recogniser and to a file at once, in the same kind of file and the same folder as a voice note on a message (`Support/DictationAudio.swift`; `Dictation.swift` still writes no file itself). When Dictate stops, the note sits on the page right after the paragraph as a Voice note block, one line in the entry's text (`[Voice note](anchorvoice://v1?f=..)`, see `Views/Journal/JournalVoice.swift`). If words were heard, a card under it offers Keep both, Text only and Voice note only; nothing is applied until a button is tapped. Text only removes the block and its file; Voice note only puts the paragraph back as it was before dictating, unless the person has typed in it since. Removing a block, deleting an entry and Clear all data remove the sound. Export for someone, the CSV and the PDF leave the block out, and the sound only travels in the encrypted backup, like voice notes on messages. **Not tried:** the file is written at the microphone's own rate and channel count, and a piece that does not match is not written; this has not been run on a phone.

**As built in VN3.** The check came out as expected: Apple's speech APIs give words with times and no speaker turns, and libraries that separate voices work from the sound, so the manual version is what is built. Settings, Journal, Label who is speaking is a third switch, off to begin with and shown only while Dictate is on. While Dictate listens, Who is speaking? offers Speaker 1 and Speaker 2; a tap starts a new line that begins with that label. Rename speakers (Journal page, three dots, only when a label is on the page) changes the label at the start of lines in that entry only, to a plain name with no colon. Nothing is stored beyond the entry's own words, and `scripts/check-dictation.mjs` fails if sound analysis or a voiceprint appears. Where a turn begins can be a word early or late because the recogniser may reword its last words.

**Never inferred.** The transcript is what was said. No tone, no sentiment, no "you sounded".

## E3. A "tidier version" of an entry: the AI Optimised block

**What it is.** In the Journal editor, a plain button (Make shorter, or Tidy up) on a text block or on a whole entry. After the consent sheet, the chosen provider returns a shorter rewrite that keeps the detail. It is shown as its own visibly different block, headed **AI Optimised**, and folded to start with. Opening it shows the rewrite; a second control shows the **original text exactly as written or transcribed**. The person taps Keep or Discard. Nothing is saved before Keep, and a discarded rewrite is gone.

**How it is stored.** Journal pages are Markdown text, and non-text blocks are single lines that `JournalBlocks.parse` already knows how to read (`JournalBlock.Kind` has `.text`, `.image` and `.card`). The block would be a fourth kind, `.assist`, written as one line holding the rewrite and the original it was made from. So there is **no model change**, no migration, the original travels with the block through backup, export and import, and deleting the original paragraph elsewhere never loses it. Opening the page in an older build shows an unknown line as plain text rather than losing it. **Check** in the patch that this really holds.

**Honesty about the output.** A model can summarise wrongly or leave something out. That is why the original is one tap away, why the block is labelled, why nothing is saved without a read and a Keep, and why the rewrite is never presented as the person's own words anywhere else (D43: left out of Export for someone, the CSV and the PDF unless ticked; when it is in, the shorter version and the words it was made from are two entries, each labelled, AI9).

**What it must not do.** Add facts, add advice, comment on feelings, change who said what, or tidy away a quote. The fixed instruction says to shorten, keep every concrete detail and name, and add nothing. That instruction is visible in the consent sheet.

## E4. A small helper for tasks, not a chatbot

**What it is.** A few plain buttons, each one action on text the person chose, none of them a conversation:

- **Break into steps** on a task: proposes steps (the nested steps from RV2), each with an optional time guess.
- **Estimate time** on a task or its steps: proposes minutes (the existing estimate field). A suggestion the person can edit; nothing is checked against it.
- **Turn into tasks** on a journal entry or a pasted braindump: proposes a list of tasks. Shown as a checklist; **nothing is created until the person ticks lines and taps Add**, the same pattern as 30q.
- **Tidy a braindump** into shorter text, a to-do list, or things to raise in a session (the existing Things to raise list). The person picks which; the app does not guess.

**Linked and traceable.** Every task or item made this way carries a link back to the entry or text it came from, and the original is never changed. A task has no such field today (checked), so the first patch adds an optional source id to a task and to a Things to raise item, with the export, import and demo changes the Definition of Done asks for.

**What it must not do.** Pick dates, set priorities or energy, decide what matters, summarise how the person has been, or add anything that is not in the text. Dates, priority and everything else stay as the person sets them.

**As built in AI4.** Turn into tasks and Tidy a braindump became one sheet, `Views/Settings/AIBraindumpSheet.swift`, with two plain buttons, Turn into tasks and Turn into things to raise, so the person picks where the words go and the app never guesses. It opens from the Journal page's three dots (this paragraph or the whole entry, shown as it is and never changed), from the list button in Add several on Tasks (pasted words, editable in the box), and from a button at the top of Things to raise. Shortening is Make shorter in the Journal (AI2) and is not repeated here. A thing to raise now has the same optional source link as a task.

**Where the buttons live.** On the screen they act on, as one ordinary button, shown only when AI tools are on and a provider is set up. Not on Now, not in a tab of its own, not in the tour.

## E5. One switch for all of it

**Settings, AI tools, Use AI tools: off by default.** When it is off:

- Make shorter, which only improves what was written, is hidden. The buttons that are the feature itself (Tidy a braindump, Break into steps, Estimate time) stay where they are, greyed out, and tapping one says AI tools are off and where to turn them on (D41, AI7). Nothing else on screen mentions AI apart from this one row and its own short help;
- no model is loaded, no network connection to any AI provider is opened, and no Local Network permission is asked;
- the guide, the tour and onboarding say nothing about it.

When it is turned off, anything half done is dropped, and the person's saved AI Optimised blocks stay as the text they are (they are the person's entries now). A separate, clearly named choice offers to turn them back into the original text, one entry at a time.

**How it is enforced.** One function, `AIGate.isEnabled`, that every AI entry point must call before it does anything. A script, `scripts/check-ai-gate.mjs`, in the same spirit as the existing check scripts, fails if a file that talks to a provider does not go through the gate. The first patch (AI0) builds the switch and the check before there is anything behind them, so no later patch can skip it. Showcase mode keeps it off. Until the first tool exists the row in Settings is in test builds only. AI1 (the consent sheet and the provider) is not a tool, so the first real tool, AI2 or AI3, is the patch that makes the row visible in every build.

**As built in AI7.** While AI tools are off, a greyed-out button (`AIOffButton`, `Views/Settings/AIOffNotice.swift`) stands in for Tidy a braindump in the Journal page's three dots, in Add several on Tasks (once words are typed) and at the top of Things to raise, and for Break into steps and Estimate time under a task's steps (once the task has a name). It is greyed but not disabled, because a button that cannot be tapped cannot explain itself. Tapping it opens an alert, AI tools are off, You can turn them on in Settings, under AI tools. It sends nothing, loads no model and opens no connection, and `scripts/check-ai-gate.mjs` fails if its file reaches a provider, if a greyed button is shown without `AIGate.showsOffButtons`, or if Make shorter is ever greyed rather than hidden. In showcase mode the buttons are not shown at all, because there is nothing to turn on there. **Not tried:** nothing was compiled or run on a phone, and a menu item may not take the grey; if it does not, the alert still says why it does nothing.

| 1 | **Apple on-device model** (Apple Intelligence, through the FoundationModels framework) | On the phone, no network | Only on devices that support it. **Check** the current iOS and model requirements. Preferred and the only one shown first. |
| 2 | **Ollama** on the person's own computer | The person's home network, or away from it after a confirmation (AI8). **As built in AI5.** Settings, AI tools, Where it runs chooses between On this phone and On my computer. For the computer the person types an address and a model name, and Look for models lists what Ollama has. Only the person's own network is accepted (a private number, a name ending in .local, or a single name), plain http is allowed to the local network only, the mobile network is never used, and the phone's Local Network question appears on the first connection, never while AI tools are off. The consent sheet shows the address and model. The code is in `Support/AIProviders.swift`, the only file allowed to open a network connection, which `scripts/check-ai-gate.mjs` enforces. AI8 changes the rule that only the home network is accepted and the mobile network is never used: see below.

**As built in AI8.** An address is home (a private number, private or link-local IPv6, a name ending in .local, a single name), Tailscale (100.64.0.0 to 100.127.255.255, fd7a:115c:a1e0::/48, a name ending in .ts.net) or internet (anything else); the last two are away. Plain http is accepted at home and to a Tailscale number; every other away address must be https, which is also all the phone's transport security allows for a name with dots. That exception, `NSAllowsLocalNetworking` in `Info.plist`, is not widened, and the check script fails if it is. An away address is not used, and Look for models is disabled, until the person taps Use this address in Settings, AI tools and agrees in the alert; the confirmation is that exact address, so a changed address is asked about again. The consent sheet still shows every time unless Don't ask again is on, with a line under the address saying whether it is on the home network or away. The home network never uses the mobile network; a confirmed away address may, and the alert and the sheet say so. **Not tried:** nothing was compiled or run on a phone.

**As built in AI6.** Settings, AI tools, Where it runs has a third choice, Other, for a service the person chooses. It is never the choice to begin with, and its address, key and model name are empty. The address must be https (a path such as /v1 is kept and `/chat/completions` is added once), the request is the common chat completions one with the key as a Bearer token and nothing else in it, and a reply that redirects is a failure. The key is in the Keychain for this phone only (not in a backup or an export), is read in one place, and Remove key takes it off. The consent sheet shows every time, shows the address and model, says Anchor cannot see how the service keeps the text, and never offers Don't ask again (D42). The app never suggests or names a service. All of it is in `Support/AIProviders.swift`, and `scripts/check-ai-gate.mjs` item 8 fails if any of those rules change. **Not tried:** nothing was compiled or run against a real service.

## The consent sheet

Every use, before anything is sent: **what** (the exact text, in full, scrollable), **to whom** (this phone, your computer at the address, or the named provider), **what happens to it** (held in memory until you keep or discard; the provider's own keeping stated for Other providers), and two buttons, Send and Cancel. "Don't ask again for this" is a switch on the sheet itself, per feature and per provider, listed in AI tools where it can be turned off. For an Other provider the recommendation is that the switch is not offered (D42).

**As built in AI1.** The sheet is `Views/Settings/AIConsentSheet.swift`. It shows the whole text that will be sent (never cut short), the fixed instruction that goes with it, where it goes and what happens to it, and has Send and Cancel pinned at the bottom. Don't ask again is a switch on the sheet for a provider that offers it, kept only if the person taps Send. Settings, AI tools lists each tool that no longer asks, with Ask again. All of it runs through `AIAsk` (`Support/AIAsk.swift`): the gate, the checks on the text, the sheet and only then the provider, and `scripts/check-ai-gate.mjs` fails if anything else sends text to a provider or if that order changes. Text over the provider's limit (4,000 characters for Apple's model, a guess to **check** on a phone) is refused before anything is sent. Turning AI tools off while the sheet is open or the model is working drops it and returns nothing.
